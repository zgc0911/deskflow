# 计划：剪贴板支持复制文件（Windows ↔ macOS，粘贴时才传）

日期：2026-11-26　状态：已批准（2026-11-26，第 4 版），已冻结。执行情况见 `docs/plans/交付-剪贴板文件复制.md`

## 批准要点

### 要做什么、为什么

- 现在 Deskflow 的剪贴板只共享文本、HTML、位图，复制文件后到另一台电脑粘贴不出文件。
- 目标：在一台电脑上复制文件或文件夹，到另一台电脑按粘贴，文件就传过来，传输时看得到进度。
- 范围是你的两台机器：Windows（服务端）和这台 Mac（客户端），两个方向都要通。

### 你已定的选择

1. 支持 Windows 和 macOS，Linux 这次不做（只保证不被改坏）。
2. 文件大小不设限，GB 级也要能传。
3. 按下粘贴时才传，切屏时不预传。
4. 尽量边传边写到粘贴的位置，用系统自带的复制进度。
5. **Windows 粘贴**：用「虚拟文件」的标准做法（远程桌面就是这么做的）。资源管理器自己读、自己写到目标文件夹、自己显示复制进度窗口。
6. **Mac 粘贴**：段 1 先试系统的「文件承诺」接口。
   - 可行：由我们把文件直接写到 Finder 给出的目标位置，进度用系统的显示。
   - 不可行：退回上一版做法。文件先传到本机临时目录，再交给系统完成粘贴；进度用 Deskflow 自己的小窗口显示。
7. 文件共享要有单独的开关。
8. Windows 安装包用你 fork 的 GitHub Actions 编。我会把提交 push 到 origin 的 master。

### 要你确认的推荐

1. **「文件承诺可行」怎么算。** Finder 里按粘贴能触发、文件能直接写到目标文件夹，就算可行。系统进度我预期是显示在文件图标上的进度条（和下载文件时一样），不是复制窗口。如果连图标进度也出不来，就在这条路上加自己的小窗口显示进度。
2. **退回做法里的小窗口。** 放在 Deskflow 的界面程序里，置顶、不抢焦点，传输超过约 1 秒才弹出：对方电脑名、当前文件、已传大小和总大小、速度，带一个取消按钮。退回做法下，Finder 在传输期间会停住等，传完才继续。
3. **Windows 上只有资源管理器这类程序能粘贴。** 桌面、文件夹窗口、Outlook 这些认「虚拟文件」的可以；微信、浏览器上传框这类只认真实路径的贴不了。Mac 上如果走文件承诺，也只有 Finder 这类程序能粘贴；走退回做法则所有程序都能粘贴。
4. **开关放在服务端设置里，和「共享剪贴板」并排，默认打开。** 它对两个方向同时生效，由服务端（你的 Windows）下发给客户端，和现有剪贴板开关的做法一致。Mac 这边没有单独的开关。
5. **现有的剪贴板大小上限（默认 3MB）不限制文件。**
6. **只做两台机器直连。** 三台以上、文件要经服务端转给第三台的情况这次不做。
7. **支持文件夹**，整个目录树一起传。符号链接和特殊文件跳过。传到 Windows 时，相对路径超过 259 个字符的文件会被跳过（系统格式的限制）。
8. **不升协议版本号。** 新版和官方旧版互连时，文字和图片照常，文件功能自动不生效。
9. **交付文件会公开。** `docs/plans/交付-剪贴板文件复制.md` 随提交推到你的 fork（公开仓库）。上游的 `docs/Readme.md` 我不动：macOS 不区分大小写，规则里的 `docs/README.md` 索引和它是同一个文件。
10. **本机要装构建工具。** 用 Homebrew 装 cmake、ninja、Qt 6、openssl、clang-format、gh，大约占 2–3 GB 磁盘。
11. **提交方式。** 每段做完提交到 master 并 push（CI 靠 push 触发）。提交信息按这个仓库现有的写法（`feat: …` 英文一行）。

### 分几段、每段做完的标准

| 段 | 做什么 | 做完的标准 |
|---|---|---|
| 1 环境与可行性验证 | 装构建工具，本机编过当前 master；跑通 fork 的 CI；用临时小程序实测下面「没核实的事」，定下 Mac 走哪条路 | 现有测试本机全过；CI 的 Windows 任务能出安装包；每件没核实的事都有实测结论，Mac 的路线写进交付文件并告诉你。出现两条路都走不通的情况就停下来找你 |
| 2 通用传输层 | 文件清单格式、新增的网络消息、列目录、从任意位置读文件、限速、取消、路径安全检查 | 自动测试：同一进程里用内存连接传一棵目录树（空文件、中文名、多级目录、一个 300MB 文件），两端 SHA-256 一致；越权路径被拒；中途断开或取消后读取方立刻收到错误；传输期间键鼠消息的延迟有上限 |
| 3 macOS 端 | 复制时读出文件清单；粘贴端按段 1 定的路线做；不把自己写入的剪贴板当成用户新复制的 | 本机自动测试。走文件承诺：用系统的「接收文件承诺」接口收进临时文件夹，哈希一致。走退回做法：另起一个进程从系统剪贴板读文件触发拉取，哈希一致；进度消息能驱动小窗口；点取消后传输停止、临时文件删掉。两条路都要满足：只复制不粘贴时不发生传输 |
| 4 Windows 端 | 复制时读出文件清单；虚拟文件数据对象；服务模式下让资源管理器读得到 | CI 的 Windows 任务编译通过（告警即报错）；自动测试：把数据对象放上剪贴板，用系统的文件夹投放接口（和资源管理器粘贴是同一套复制引擎）拷到临时目录，哈希一致；产出安装包 |
| 5 开关 | 新设置项、服务端设置窗口里的勾选框、下发给客户端、中文翻译 | 自动测试：开关的存取和下发正确；关掉后不发清单、不应答请求、收到的清单被忽略。我在本机跑起界面，截图核对 |
| 6 两台真机联调与收尾 | 你按验收清单走一遍；我按结果修；更新协议文档；写收尾总结 | 验收清单全部正常；CI 上 Windows、macOS、Linux 的编译和测试都通过 |

### 怎么证明做对了

- **自动测试**：传输前后比对哈希；越权路径、断线、取消、源文件中途被删这几类用例；键鼠消息延迟上限。
- **真实系统**：macOS 上走真实的系统剪贴板；Windows 上在 CI 的真实系统里走系统的复制引擎。
- **回归**：现有单元测试在本机和 CI 的三个系统上全过。
- **变异检查**：路径安全检查、大小校验这类核心校验，去掉后对应测试必须失败。
- **审核**：每段我逐文本自审。段 4 结束后做一次三切片审核（传输层、macOS 端、Windows 数据对象），发现由我按证据逐条核实。预计多等 20 分钟左右。

### 你要亲手做的

- **段 1 开始时，2 步，约 5 分钟**：在 fork 的 GitHub 页面开启 Actions；在终端登录一次 gh（`! gh auth login`），让我能看 CI 日志。
- **段 1 中途，1 到 2 步，约 3 分钟**：我放好测试用的剪贴板后，请你在 Finder 里按一次粘贴，告诉我看到了什么。我能自动操作 Finder 的话就不麻烦你。
- **最终验收，10 步，约 30 分钟**：两台机器装新版（Mac 上要重新给辅助功能权限）；小文件、文件夹、1GB 大文件各走两个方向，看进度显示；确认大文件传输时鼠标键盘照常；关掉开关后文件不再共享、文字照旧；传输中断线后两端不崩、不留半截文件。

### 风险和没核实的事

没核实的，都放在段 1 先实测：

1. Finder 的粘贴认不认「文件承诺」。我估计不认，那样 Mac 走退回做法。
2. 走退回做法时，Finder 什么时候向我们要文件、最长肯等多久。如果它等几十秒就放弃，大文件要改成「第一次粘贴开始传，传完再粘贴一次」，那时我会找你确认。
3. Windows 资源管理器对我们的虚拟文件是不是边读边写并显示进度。这是标准做法，把握较大，在 CI 的 Windows 上验。
4. Windows 服务模式下核心进程是 SYSTEM 身份，资源管理器是你的登录身份，跨身份读内容流要额外放开权限。CI 测不了，只能在你的 Windows 上验。不通的话，退路是让 Windows 上的 Deskflow 改用非服务模式运行。
5. fork 的 CI 没有签名密钥时，Windows 任务能不能独立出包。macOS 任务预计会因缺密钥失败，不影响 Windows 包。

已知风险：

- Windows 代码我在本机编不了，只能靠 CI 试，每轮约 30 分钟，段 4 可能要多轮。
- Windows 服务模式下，网络盘和 OneDrive 未下载到本地的文件可能读不到。
- Mac 上自己编的版本签名和官方版不同，要重新给辅助功能权限；第一次读「桌面、文稿、下载」里的文件会弹权限框。
- 走退回做法时，剪贴板管理工具（Paste、Maccy 之类）会在复制后立刻读剪贴板里的文件，相当于提前触发传输。
- 以后上游如果自己做了文件剪贴板，合并上游时会冲突。
- 测试期间会临时占用这台 Mac 的系统剪贴板。
- 段 3 和段 6 要停掉这台 Mac 上正在运行的官方 Deskflow，换成新编的版本，期间键鼠共享会中断。动之前我会先说。

## 方案概要

### 现状（调查结论）

- 剪贴板格式只有三种，定义在 `src/lib/deskflow/IClipboard.h`。对端不认识的格式编号在解包时被丢弃，所以加新格式不会弄坏旧版。
- 剪贴板内容是整块读进内存、切成 512KB 的块、一次性排进发送队列的。大内容会堵住同一条连接上的键鼠消息和保活消息，所以文件不能走这条路。
- 上游在 2025 年删掉了整套文件拖放代码（提交 `5365e34f0`），协议里只剩 `DFTR`、`DDRG` 两条作废定义，不复用。
- 核心进程 `deskflow-core` 的主线程跑 Qt 的事件循环，网络和键鼠处理在另一条线程（`src/apps/deskflow-core/deskflow-core.cpp`、`src/lib/deskflow/App.cpp`）。读文件的请求可以在别的线程上等数据，不影响键鼠共享。
- Windows 上核心线程已经初始化了 OLE（`src/lib/platform/MSWindowsComputer.cpp`），默认以服务模式、SYSTEM 身份运行（`src/lib/common/Settings.cpp`）。
- 核心进程到界面程序已经有一条状态通道（`src/lib/deskflow/ipc/CoreIpc.cpp`，界面在 `src/lib/gui/core/CoreProcess.cpp` 里收），现在用来报连接状态。退回做法的进度和取消走这条通道。
- 现有的剪贴板开关在服务端设置窗口（`src/lib/gui/dialogs/ServerConfigDialog.ui`），经选项下发给客户端。新开关照这个做法。
- 本机和服务端的剪贴板读写都经过 `deskflow::Computer`（`src/lib/deskflow/Computer.cpp`），是接入文件功能的唯一入口。
- 界面上的文字在构建时会自动更新 `translations/*.ts`，CI 会检查构建后仓库有没有变化，所以加了界面文字要把更新后的翻译文件一起提交。

### 做法

**复制的一端（发送方，两个系统相同）**

- 系统剪贴板里有文件时，读出顶层的文件和文件夹路径。Windows 读 `CF_HDROP`，macOS 读 `public.file-url`。
- 发给对端的只有一份文件清单：顶层每一项的名字、大小、修改时间、是不是文件夹，加一个清单编号。本机的绝对路径不出本机。
- 清单编号由内容算出，同样的内容得到同样的编号，避免现有的「内容没变就不重发」判断失效。
- 对端来列目录或读文件时，按清单编号找到本机路径再应答。每个请求先做路径检查：不许 `..`、绝对路径、符号链接跳出被复制的范围；只响应当前这份清单。

**粘贴的一端：Windows**

- 收到带文件清单的剪贴板后，往系统剪贴板放一个数据对象，里面是「文件描述」和「文件内容流」两种格式，同一份剪贴板里的文字也由它提供。
- 资源管理器粘贴时先要文件描述。这时向对端把目录树列全，填好每个文件的相对路径、大小、时间。
- 然后资源管理器逐个打开内容流来读。每次读都转成向对端要数据，读多少给多少。写盘和进度窗口都是资源管理器自己的。
- 数据对象声明支持后台操作，这样资源管理器在后台线程里复制，窗口不卡。
- 核心进程启动时放开 COM 调用权限，让登录用户的资源管理器能调到 SYSTEM 身份的核心进程。

**粘贴的一端：macOS，首选「文件承诺」**

- 收到带文件清单的剪贴板后，往系统剪贴板为每个顶层项目放一个文件承诺。
- Finder 粘贴时把目标文件夹告诉我们。我们在后台线程里向对端要数据，直接写到那个文件夹，同时向系统发布进度。
- 中途失败就删掉写了一半的文件，把错误报给系统。

**粘贴的一端：macOS，退回做法**

- 收到带文件清单的剪贴板后，往系统剪贴板放「文件」这个格式，但先不给内容。
- 别的程序真正来取文件时（也就是粘贴时），另起一条工作线程向对端要目录列表和文件内容，写进用户缓存目录下的临时目录，传完后把临时目录里的路径交给系统。主线程在这期间等着，但仍能收发状态通道上的消息。
- 工作线程先统计总大小，再边传边把进度经状态通道发给界面程序，界面程序弹小窗口。点取消后工作线程停止，告诉对端不用再发，删掉半截文件，这次粘贴落空。
- 再粘贴一次不重传，直接用临时目录里已有的文件。临时目录在核心进程启动时清空，换了新剪贴板后清掉更早的。

**开关**

- 新增设置项「通过剪贴板共享文件」，在服务端设置窗口里放在「共享剪贴板」下面，「共享剪贴板」关掉时它变灰。
- 关掉后：本机不再发文件清单，不应答请求，收到的清单也忽略。服务端把这个状态作为选项下发给客户端。

**网络消息**

- 新增四条消息：请求（列目录，或从某个位置读文件）、应答数据块、放行额度、取消。
- 发送方只在接收方放行的额度内发数据，接收方用掉了再放行下一批。所以两端内存占用有上限，键鼠消息能插在数据块之间。
- 同一时间允许几路读取并行。
- 新消息只发给「给我发过文件清单」或「向我发过请求」的对端，所以旧版对端永远收不到不认识的消息。
- 服务端把一个客户端的剪贴板转给另一个客户端时，去掉文件清单（这次不做中转）。

**改动落点（模块级）**

- `src/lib/deskflow/`：新格式、文件清单的编解码、清单登记、请求的发起与应答、`Computer` 里的接入点。
- `src/lib/client/ServerProxy*`、`src/lib/server/ClientProxy1_6*`、`Server.cpp`、`Config.cpp`：收发新消息、转发时去掉清单、开关的下发。
- `src/lib/platform/`：macOS 剪贴板读文件路径、粘贴端；Windows 剪贴板读文件路径、虚拟文件数据对象和内容流。
- `src/apps/deskflow-core/`：Windows 上启动时的 COM 权限设置。
- `src/lib/gui/`、`src/lib/common/Settings.*`、`translations/`：开关；退回做法下还有进度小窗口。
- `src/unittests/`：各层的测试。
- `docs/dev/protocol_reference.md`、`docs/Configuration.md`：补上新格式、新消息、新设置项的说明。

函数、文件和测试的清单，开工时写进交付文件 `docs/plans/交付-剪贴板文件复制.md`。

## 验证

- 本机：`cmake -S. -Bbuild -G Ninja` 配置，`cmake --build build` 编译并跑测试；提交前用 clang-format 20.1.0 格式化（CI 的格式检查不过就不会开始编译），按 REUSE 规则检查新文件的版权头。
- CI：push 到 origin 的 master 后看 `Continuous Integration` 这条流水线。Windows 任务的编译、测试和安装包是段 4 的证据。
- 段 1 的实测用临时小程序做，放在会话的临时目录里，不进仓库，测完删掉。
- 界面上的勾选框和小窗口：我在本机启动新编的界面程序，截图核对。
- 最终由你在两台真机上按验收清单走一遍。清单在段 6 开始时写进交付文件，格式按 `/docs-convention` §1。
